### Post-Export
Exported .zip files currently follow the internal folder hierarchy of the graph detailed below:
```
<file_name>.zip
├── .godot
│   ├── imported
│   │   ├── icon.png-<original_path_md5>.ctex
│   │   └── ...
│   ├── exported
│   │   ├── exported-<original_path_md5>-<map_id>.scn
│   │   └── ...
│   ├── global_script_class_cache.cfg
│   ├── uid_cache.bin
│   └── ...
├── art
│   └── textures
│       ├── anon_icon.png
│       └── boot_splash.png
├── custom_levels
│   └── <map_id>
│       ├── level.json
│       ├── icon.png.import
│       ├── <map_id>.tscn.remap
│       └── ...
└── project.binary
```
The exported file is immediately ready for import with no further changes. Whilst the current export method is imperfect and leaves some non-essential files, none of these seem to significantly impact the game process post-load. How these files are handled natively and how I plan to handle them during import will be discussed in 3.c. and 3.d.
### Essential Files
- The `custom_levels/<map_id>/` folder contains all remaps that are generated by the export process of the source files . Most files (with certain exceptions like shaders) are converted to their respective binary formats on export, such as `.gd -> .gds`, or `.tscn -> .scn`. The original files are replaced with `.remap` or `.import` files, which link to their binary exported versions whilst still retaining the original structure of the map. This folder also contains `level.json`.
- The `.godot/imported/` and `.godot/exported/` folders contain the aforementioned binary converted files and are automatically generated on export. Map developers should never interact with these files in this form, as binary files will become unusable if modified using conventional text editors. 
- The `.godot/` folder also contains a variety of other essential files such as `uid_cache.bin`, `global_script_class_cache.cfg`, etc. These cache files store information such as `uid://` to `res://` mappings, class names, etc.
### Non-Essential Files
- The `art/textures/` folder contains `anon_icon.png` and `boot_splash.png`, both of which are considered essential files by Godot. If the packs that map developers were exporting were a full game, these indeed would be essential, but they are not for our purposes. These can be safely stripped, which prevents overwriting in the event that they have been modified.
- The `project.binary` file contains information about engine-level project settings, such as autoloads and keybinds. Similar to the previous point, this is considered essential by Godot for full game packs. This can be safely stripped, but should never cause any issues if loaded from within a pack.
### Potential Changes
- A future map development plugin should automatically clean excess files (like `project.binary`) on export, though this cannot be left entirely to the plugin. The import process will still clean all imported zips to avoid overwriting key files just in case, but cleaning them at export also will reduce file size and quantity of files required for verification.
